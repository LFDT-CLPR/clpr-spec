# Implementation Discrepancies

## Purpose

This record lists where the v0.2 source text disagreed with the implementations, and how the rewritten v0.2 specification resolves each case (Part A). It then lists where an implementation does not conform to the rewritten specification (Part B), and the rules on which the implementations disagree and the text chose one behavior, which are to be confirmed (Part C). The baseline is the EAP v0.2 specification text (archived in [`archive/eap-v0.2-source/`](../eap-v0.2-source/README.md)). The implementations are the Hiero implementation (release 0.2), the EVM contracts (release 0.2), and the EVM endpoint (release 0.8). All behavior was established by reading the implementation code. Consequences derived from the code but not observed in a run are marked "inferred from code".

## Part B. Implementations that do not conform to the v0.2 specification

### Hiero implementation (release 0.2)

| # | Rule | Behavior | Impact on interoperability |
|---|---|---|---|
| BH-1 | [Bundle §3](../../protocol/bundle.md#3-partial-bundles), [Verifier interface §3](../../protocol/verifier-interface.md#3-verifybundle) | The verifier return has 6-field metadata in which `next_message_id` is one past the bundle's last message, with no separate last-message values ([Hiero Verifier API §5](../../ledgers/hiero/verifier-api.md#5-conformance)). | Partial bundles cannot be expressed. A partial bundle from the EVM endpoint is assigned the wrong first id and running hash and is rejected (inferred from code). A verifier written for the EVM Verifier API cannot be used on Hiero. |
| BH-2 | [Channel state transitions §5](../../protocol/channel-state-transitions.md#5-closing-and-draining) | DRAINED→CLOSED omits `received_message_id ≥ metadata.next_message_id − 1`. The Hiero verifier return does not carry the sender's real `next_message_id` ([Hiero Verifier API §5](../../ledgers/hiero/verifier-api.md#5-conformance)), so the Service cannot evaluate this condition. | Hiero can close before it has received every message in the peer's queue. Under BH-1 the condition always holds after a bundle that carries messages. Low (inferred from code). |
| BH-3 | [Ledger configuration §5.2](../../protocol/ledger-configuration.md#52-sending) | Enqueues a due ConfigUpdate during bundle processing in any status, including CLOSING and DRAINED. | Peers receive CONTROL messages on closing channels. ## Part C. Choices between implementations

Rules where the implementations differed and the v0.2 text chose one of them. The Maintainers confirmed each choice for v0.2.

| # | Rule | Text chose | Implementations |
|---|---|---|---|
| C-1 | New anchor epoch after epoch boundary headers ([QBFT epoch §7](../../ledgers/besu/proof-schemes/qbft-epoch.md#7-trust-anchor-changes)) | `E + k`, the epoch of the last boundary header carried. | The new trust anchor's epoch is the epoch of the last boundary header carried (Hiero implementation and EVM endpoint agree); the EVM legacy verifier differs. |
| C-2 | Receipt of reply status value 6 ([Messaging §7](../../protocol/messaging.md#7-replies)) | Reserved; MUST NOT be produced; a receiver MAY accept it with no penalty instead of rejecting under strict decoding. | EVM contracts define it as NOT_HANDLED, accept it and never produce it. Hiero neither defines nor produces it. The EVM endpoint's schema lacks it. |
| C-3 | Pausing on a missing reply ([Messaging §8](../../protocol/messaging.md#8-response-ordering)) | A receiver MAY pause. | EVM contracts pause; Hiero does not. |
| C-4 | Effects of a response ordering violation ([Channel state transitions §6](../../protocol/channel-state-transitions.md#6-pause-and-resume)) | The acknowledgement MAY be applied; on CLOSING or DRAINED the bundle MAY be rejected. | EVM contracts apply the acknowledgement and reject on CLOSING. Hiero does not apply it and accepts the bundle with no change. |
| C-5 | Queue depth ([Messaging §5](../../protocol/messaging.md#5-enqueue)) | Reject when `next_message_id − 1 − acked_message_id ≥ max_queue_depth`. | EVM contracts match. Hiero is stricter by one (BH-14). |
| C-6 | Responder on a CLOSED channel ([Endpoint sync §3.2](../../protocol/endpoint-sync/README.md#32-rules)) | MAY send a bundle that reports CLOSED. | The EVM endpoint sends one; Hiero's endpoint refuses the sync. |
