# EAP 0.2 Specification Baseline

Spec release **0.2** is the second Early Access Program release (0.1 being the original EAP release). Three
implementation teams have implemented the ADRs merged since 0.1 unevenly, and several merged changes cannot be
delivered in the Hiero implementation by the 0.2 feature cut-off. This ADR fixes the 0.2 baseline to what can be
implemented and made interoperable across Hiero and EVM ledgers in that window: it retains some merged changes, reverts
others, and corrects the specification where it diverges from the agreed design. Where the implementations already
interoperate, the specification documents their behaviour rather than changing it.

**Changes in this ADR:**
- Mutual TLS between CLPR Endpoints is removed; endpoints use ordinary TLS for confidentiality only.
- All CLPR Endpoint interactions are served on a single advertised port.
- `ClprEndpoint` keeps `tls_certificate` and `account_id`; neither is used by the network.
- Two-phase streaming sync is the only normative endpoint sync method.
- `ChannelSyncData` is reverted to `ClprQueueMetadata`, which carries the sender's proven Channel state; a bundle may
  carry a proper prefix of the pending messages.
- `verifyBundle` returns the ID and running hash of the bundle's last message alongside `ClprQueueMetadata`.
- The on-chain endpoint manifest is the only endpoint source; there is no seed-endpoint fallback. The manifest proof at
  `completeChannel` is optional.
- A Channel drains only once every Data Message it sent is answered, and a bundle moves it to `CLOSED` only after it
  has received every message in the peer's proven queue.
- Message redaction is deprecated: implementations accept it, and it SHOULD NOT be used. The running hash stays
  `SHA-256(prev ‖ SHA-256(serialized_payload))`.
- CLPR protobuf definitions keep the implemented field numbers. Deprecated fields and values keep their numbers;
  `ClprLedgerConfiguration.endpoints = 6` is unused.

---

## 1. Problem Description

### 1.1 The specification has outrun the implementations

Five ADRs have been merged since 0.1 (`2026-07-02` Channel context, `2026-07-03` endpoint manifests, `2026-07-14`
streaming sync and mTLS, `2026-07-17` `ChannelSyncData`, `2026-08-01` redaction removal). Each implementation has
adopted a different subset. The main-branch specification therefore describes a protocol that no pair of
implementations speaks, and there is no single document an EAP participant can conform to.

### 1.2 mTLS cannot be delivered and is not the chosen identity mechanism

§1.2 and §3.1.2 require each endpoint to publish a self-signed ECDSA P-384 CA certificate in the manifest and to
present an in-memory Ed25519 leaf at an mTLS handshake. The Hiero implementation runs mTLS on a dedicated port with a plaintext
fallback on the HAPI port; the EVM endpoint is plaintext-only. Peer identity is to be established by a future
signed-nonce mechanism rather than transport certificates. Storing a certificate per endpoint in EVM contract storage is
also a recurring cost with no 0.2 consumer.

### 1.3 Endpoint interactions are split across ports and method names

The Hiero implementation serves `ClprEndpointService` on either a dedicated mTLS port or the shared HAPI port, and exposes the
two-phase sync as `streamingSync` alongside a unary `sync` with a different payload shape. The EVM endpoint exposes
two-phase sync as `sync`. gRPC routes by the full method path, so the two cannot interoperate.

### 1.4 `ChannelSyncData` cannot be delivered for 0.2

`ChannelSyncData` requires a separately stored, separately proven state record and new `anchor_message_id` /
`anchor_running_hash` verifier outputs. The Hiero implementation implements `ClprQueueMetadata`, not `ChannelSyncData`, and cannot
migrate within the 0.2 window.

### 1.5 Some verifiers force every pending message into a bundle

The `clpr-smart-contracts` verifiers derived the bundle's end from the Channel's own `next_message_id` and
`sent_running_hash`, so a bundle had to reach the true tail of the outbound queue. A backlog larger than
`max_messages_per_bundle` or `max_sync_bytes` can never be delivered, and the Channel stalls. The pre-`2026-07-17`
wording of `ClprQueueMetadata` (§4.2 Step 3: "the last message's ID MUST equal `ClprQueueMetadata.next_message_id - 1`")
permitted this reading.

### 1.6 A Channel can close before its Responses arrive

A side transitions `CLOSING → DRAINED` once no Data Message above `acked_message_id` remains, and
`DRAINED → CLOSED` once the peer reports `DRAINED` and the local outbound queue is acknowledged. Neither condition
waits for the peer's Response Messages to this side's Data Messages. Once bundles may stop short of the sender's
queue tail, the receiver cannot infer from the peer's status that those Responses have been delivered, so a Channel
can close with Responses undelivered and Data Messages orphaned in its outbound queue.

### 1.7 The double-hash running hash is unsafe

Both implementations compute `SHA-256(prev ‖ SHA-256(serialized_payload))`. Because a message's contribution to the
chain is the digest of its payload, an endpoint can substitute the digest for the payload (redact) or restore it
(unredact) without breaking the chain, overriding the CLPR Service's decision about what a message contains. The
EVM CLPR Service hashes the payload bytes it receives, so against it an endpoint cannot redact (a substituted digest
fails the running-hash check), but it can still unredact by supplying the original payload.

### 1.8 Protobuf numbering is not clean

The Hiero implementation carries a deprecated `endpoints = 6` in `ClprLedgerConfiguration` (shifting the trust-anchor fields to 7
and 8), `ClprEndpoint.account_id = 3`, and redaction artifacts (payload variant 4, `REDACTED = 4`) plus an unspecified
`CHANNEL_CLOSED = 5` reply status. None of these are in the main-branch specification, and under the strict "reject unrecognized
fields" rule (§1) a conforming peer rejects messages that contain them.

## 2. Options Considered and Non-Goals

### 2.1 Options Considered

**Ship main-branch `ChannelSyncData` for 0.2 — rejected.** It is the better long-term structure, but it requires a new
proven state record on Hiero and a changed verifier interface on every chain; the Hiero implementation cannot deliver this by the
cut-off. Partial-prefix bundles, which are the part 0.2 actually needs, can be expressed by returning the bundle's
last message ID and running hash alongside `ClprQueueMetadata` (§3.3.3).

**Keep mTLS and defer TLS changes — rejected.** mTLS is the only in-spec transport, yet no two implementations can
complete an mTLS handshake with each other, and the identity it provides is being replaced by a different mechanism.

**Serve TLS and plaintext on separate advertised ports — rejected for 0.2.** It doubles the manifest's endpoint
description and requires publishing which port is which. A single port with client-driven negotiation needs no
additional on-chain data.

**Renumber the protobufs contiguously and drop deprecated fields for 0.2 — deferred.** It is a lockstep wire change for
every implementation and for state already proven between them (for example the Hiero `ClprChannel` leaf). The
implemented numbering interoperates today, and receivers ignore the unused `ClprLedgerConfiguration.endpoints = 6`.

**Switch to a single-hash running hash for 0.2 — deferred.** It is also a lockstep change on every chain and endpoint.
Redaction SHOULD NOT be used, and an EVM receiver rejects a digest substituted for a payload (§1.7).

**Remove redaction, `tls_certificate` and `account_id` for 0.2 — deferred.** The implementations keep them. A
deprecated feature that SHOULD NOT be used, or an optional field the network does not use, does not affect
interoperability.

**Require the manifest proof at `completeChannel` — deferred.** Every verifier accepts an empty proof and starts the
Channel at manifest version 0; the first manifest-carrying bundle then installs the peer manifest.

### 2.2 Non-Goals

- Peer identity during sync (signed nonce in `BundleRequest`) — tabled for 1.0.
- Serving the endpoint interface on both a TLS and a non-TLS advertised port — tabled for 1.0.
- `ChannelSyncData` as a separately proven record — tabled for a later release.
- Renaming `ClprLedgerConfiguration` to `ClprServiceConfiguration` — tabled for 1.0.
- Channel bonds, reusable Connector IDs, and proportional bundle-cost sharing — tabled for 1.0.
- Supplemental endpoint RPCs (`discoverEndpoints`, `getLedgerConfiguration`); implementations MAY expose them outside
  this specification.
- Bumping `ClprLedgerConfiguration.protocol_version`.
- Removing `ClprLedgerConfiguration.endpoints = 6` — tabled for 0.3.
- Removing message redaction (`redactMessage`, payload variant 4, `REDACTED`) — tabled for 0.3.
- Contiguous protobuf renumbering and removal of `tls_certificate`, `account_id` and `CHANNEL_CLOSED` — tabled for a
  later release.
- The single-hash running hash — tabled for a later release.
- A mandatory endpoint manifest proof at `completeChannel` — tabled for a later release.

## 3. The Solution

### 3.1 Endpoint transport

#### 3.1.1 Single port

Each CLPR Endpoint serves the entire `ClprEndpointService` on the single address and port advertised in its
`ClprEndpoint.service_endpoint`. All RPCs share that port as HTTP/2 streams.

#### 3.1.2 TLS

- An endpoint server SHOULD serve TLS on its advertised port using a certificate chaining to a publicly trusted root.
- An endpoint server MAY additionally accept plaintext HTTP/2 on the same port.
- An endpoint server MUST NOT request or require a client certificate.
- A client MUST attempt a TLS handshake first. If the handshake fails, the client MAY retry the connection in
  plaintext.
- A client MAY skip validating the server certificate chain and hostname or IP.
- No endpoint identity is derived from the transport. Integrity and authenticity of all protocol data are provided
  by the state proofs verified by the Channel's verifier.

#### 3.1.3 `ClprEndpoint`

```protobuf
// An endpoint participating in CLPR syncs for this CLPR Service.
message ClprEndpoint {
  // Network address and port serving ClprEndpointService (§3.1.1). Optional;
  // omit for private networks that only initiate outbound syncs.
  ServiceEndpoint service_endpoint = 1;

  // DER-encoded TLS certificate. Optional. Not used by the network: no endpoint
  // identity or transport security is derived from it (§3.1.2).
  bytes tls_certificate = 2;

  // Platform-specific account identifier of the endpoint operator. Optional.
  // Not used by the network.
  bytes account_id = 3;
}
```

`registerEndpoint`, `addEndpoint`, and `updateEndpointManifest` (§6.5) always accept an empty `tls_certificate` and MAY
validate a non-empty one. The EVM CLPR Service accepts a non-empty certificate only if it parses as a DER X.509
certificate with an `rsaEncryption` key whose modulus is at least 256 bytes (nominally 2048 bits); it checks no
signature or validity period.

### 3.2 Endpoint sync service

```protobuf
service ClprEndpointService {
  rpc sync(stream ClprSyncPayload) returns (stream ClprSyncPayload);
}
```

`sync` is the only normative RPC. The CLPR protobuf definitions are in `package proto;`, so the full method path
is `/proto.ClprEndpointService/sync`, and every implementation MUST use it. `ClprSyncPayload`, `BundleRequest`, `BundleResponse`, `ClprChannelStatus`, and the
two-phase exchange are as specified in §1.5 and §3.1.4. Endpoints initiating a sync MUST use `sync`.

### 3.3 `ClprQueueMetadata`

#### 3.3.1 Definition

```protobuf
// Queue metadata returned by verifyBundle. Every field is the sender's proven
// Channel state at the proof's block; the last two fields are informational.
// A bundle may carry only a prefix of the sender's queue, so next_message_id
// and sent_running_hash can run ahead of the bundle's messages.
message ClprQueueMetadata {
  // The sender's Channel.next_message_id.
  uint64 next_message_id = 1;

  // The sender's Channel.sent_running_hash: its running hash after its latest
  // enqueued message.
  bytes sent_running_hash = 2;

  // Highest ID of the receiver's messages that the sender has received and
  // processed.
  uint64 received_message_id = 3;

  // The sender's running hash over all messages it has received on this
  // Channel.
  bytes received_running_hash = 4;

  // The sender's Channel status.
  ClprChannelStatus status = 5;

  // The sender's Channel.trust_anchor_id. Informational.
  bytes trust_anchor_id = 6;

  // The sender's Channel.endpoint_manifest.version. Informational.
  uint64 endpoint_manifest_version = 7;
}
```

- The verifier MUST derive every `ClprQueueMetadata` field from the sender's proven Channel state.
- The bundle's own last message is identified by the separate `last_message_id` and `last_message_running_hash`
  outputs (§3.3.3), which the verifier MUST prove: from that message's queue entry (its message ID and
  `running_hash_after_processing`), or from the sender's Channel state when it is the sender's latest message. When
  the bundle carries no messages they are `0` and empty.
- The verifier is not required to populate fields 6 and 7. The receiving CLPR Service MUST NOT use them to drive
  state changes.

#### 3.3.2 Channel state

`next_message_id`, `received_message_id`, and `status` are fields of `Channel` (§2.1), alongside `acked_message_id`,
`sent_running_hash`, and `received_running_hash`. `ChannelSyncData` is removed.

#### 3.3.3 Verifier interface

```
function verifyBundle(bytes bundle_payload, bytes trust_anchor, ChannelContext ctx)
  returns (ClprQueueMetadata, ClprMessagePayload[],
           uint64 last_message_id, bytes last_message_running_hash,
           bytes new_trust_anchor, bytes new_trust_anchor_id,
           ClprEndpointManifest new_endpoint_manifest)
```

`anchor_message_id` and `anchor_running_hash` are replaced by `last_message_id` and `last_message_running_hash`. The
verifier MUST reject a bundle whose first message (`last_message_id − n + 1`) is at or before the sender's proven
`acked_message_id`. Protobuf messages and pseudo-API signatures are the normative pattern; platform-specific
specifications adapt their concrete representation (ABI tuples, storage layout) while preserving their semantics.

#### 3.3.4 Bundle construction

A bundle carries a contiguous run of the sender's outbound queue ending at any message the sender chooses, subject to
`max_messages_per_bundle` and `max_sync_bytes`. Let `s = max(BundleRequest.current_received_message_id,
Channel.acked_message_id)`. The run is empty when `s ≥ Channel.next_message_id − 1`; otherwise it MUST start at
`s + 1`. The request is unproven and only shapes the bundle; an overstated request yields a
bundle that the requestor's ledger rejects for a gap.

Messages before the last one in the run are secured by the proven running hash of the last message
(`last_message_running_hash`) and SHOULD NOT be individually state-proven.

#### 3.3.5 Bundle processing (§4.2)

Let `n` be the number of returned messages, `m` the returned `ClprQueueMetadata`, and `l` and `h` the returned
`last_message_id` and `last_message_running_hash`.

- **Step 1a (progress).** Criterion 1 (new messages) holds when `n > 0` and `l > Channel.received_message_id`.
  Criterion 4 (acknowledgement) holds when `m.received_message_id > Channel.acked_message_id`. Criteria 5(b) and
  5(c) follow §3.3.6. The other criteria are unchanged.
- **Step 2 (size).** `max_messages_per_bundle` counts every message carried in the bundle, including messages the
  receiver has already received.
- **Step 3 (replay defense).** `m.next_message_id` MUST be ≥ `Channel.received_message_id + 1`. When `n > 0`:
  `n ≤ l < m.next_message_id` and `Channel.received_message_id ≤ l ≤ Channel.received_message_id + n`, so the
  first message ID is ≥ `1` and ≤ `Channel.received_message_id + 1`. The messages carry IDs `l − n + 1 … l`.
  Messages with ID ≤ `Channel.received_message_id` are skipped: they are not re-hashed or dispatched. Any
  violation rejects the bundle.
- **Step 4 (running hash).** Fold the non-skipped messages onto `Channel.received_running_hash` (§3.4). When `n > 0`
  the result MUST equal `h`, including when every message is skipped. When `n = 0` and
  `m.next_message_id = Channel.received_message_id + 1`, `m.sent_running_hash` MUST equal
  `Channel.received_running_hash`. If either required equality fails, reject the bundle.
- **Step 5 (acknowledgement).** If `m.received_message_id > Channel.next_message_id − 1`, or
  `m.received_message_id < Channel.acked_message_id` (the sender's proven state is older than one already processed),
  reject the bundle. If `m.received_message_id > Channel.acked_message_id`, set
  `Channel.acked_message_id := m.received_message_id`.
- **Step 5a** uses `m.status` as before.
- **Step 5c (config propagation)** is skipped unless `Channel.status` was `ACTIVE` or `PAUSED` when the bundle
  arrived, so a `ConfigUpdate` cannot advance `Channel.next_message_id` on a closing Channel and block
  `DRAINED → CLOSED`. The status is taken before this bundle's Step 5a transition, so a bundle that moves an `ACTIVE`
  Channel to `CLOSING` still propagates a pending configuration.
- **Step 7 (drain check)** follows Step 6 dispatch; see §3.3.6.

#### 3.3.6 Drain condition

A Channel transitions `CLOSING → DRAINED` when no Data Messages remain in its outbound queue. Data Messages are
retained after acknowledgement until their Response Message is received and matched, so this condition holds only
when every Data Message this side sent has been acknowledged and answered; this side's own Response Messages to the
peer may still be draining. The drain check is Step 7, evaluated after Step 6 dispatch, so a Response delivered in
the same bundle counts. `closeChannel` on an `ACTIVE` or `PAUSED` Channel transitions it to `CLOSING`, and to
`DRAINED` in the same step under the same condition.

`DRAINED → CLOSED` requires the peer to report `DRAINED` or `CLOSED`, `Channel.acked_message_id ≥
Channel.next_message_id − 1`, and `Channel.received_message_id ≥ m.next_message_id − 1`: every message in the peer's
proven queue has been received, so nothing the peer sent is still in flight.

- **Criterion 5(b)** holds when `Channel.status = CLOSING` and no Data Messages remain in the outbound queue: every
  Data Message this side has sent is covered by `max(Channel.acked_message_id, m.received_message_id)` and answered.
- **Criterion 5(c)** holds when `Channel.status = DRAINED`, `m.status ∈ {DRAINED, CLOSED}`,
  `max(Channel.acked_message_id, m.received_message_id) ≥ Channel.next_message_id − 1`, and
  `Channel.received_message_id ≥ m.next_message_id − 1`.

The admin may force a `DRAINED` Channel to `CLOSED` only when `Channel.acked_message_id ≥ Channel.next_message_id − 1`,
so that only the peer's close-notification is missing and nothing is abandoned; otherwise `closeChannel` on a
`DRAINED` Channel is rejected, as it is on `CLOSING` and `CLOSED` Channels. Admin authority is limited to recovering a
stuck protocol, never to discarding messages.

### 3.4 Running hash

```
running_hash_after_processing = SHA-256(previous_running_hash ‖ SHA-256(serialized_payload))
```

The previous running hash is 32 bytes. `serialized_payload` is the protobuf serialization of the `ClprMessagePayload`.
Message redaction (`redactMessage`, payload variant 4 `redacted_message`, reply status `REDACTED = 4`) and the reply
status `CHANNEL_CLOSED = 5` are deprecated: receivers accept them, and they SHOULD NOT be used. A receiver answers a
`redacted_message` with a `REDACTED` Response Message. The EVM CLPR Service hashes the payload bytes it receives, so it
rejects a bundle that carries a redacted payload in place of the original.

### 3.5 Endpoint manifest

The on-chain `ClprEndpointManifest` (§1.2, §2.4, §6.5) is the only source of endpoints on every CLPR Service. There is
no seed-endpoint or manifest-disabled mode. `completeChannel` SHOULD supply `endpoint_manifest_proof_bytes`, and
`verifyConfig` then returns the peer manifest. When the proof is empty, `verifyConfig` returns the uninitialized
manifest (version 0), and the Channel takes the peer manifest from the first bundle that carries a manifest proof
(§4.2 Step 1b). A supplied proof that yields version 0 is rejected. `ClprEndpointManifest` carries `ClprEndpoint` as
defined in §3.1.3.

### 3.6 Protobuf numbering

CLPR protobuf definitions keep the numbering the 0.2 implementations use. A field or value marked deprecated keeps its
number, and receivers accept it. The normative numbering is the one in `clpr-service-spec.md` §1. In particular:

- `ClprLedgerConfiguration`: `endpoints = 6` is deprecated and unused; receivers ignore it, whether or not it is
  populated. `initial_trust_anchor = 7`, `initial_trust_anchor_id = 8`.
- `ClprEndpoint`: `service_endpoint = 1`, `tls_certificate = 2`, `account_id = 3` (§3.1.3).
- `ClprMessagePayload`: variants 1–3, and the deprecated variant 4 `redacted_message` (§3.4).
- `ClprMessageReplyStatus`: `SUCCESS = 0` through `CONNECTOR_UNDERFUNDED = 3`, and the deprecated `REDACTED = 4` and
  `CHANNEL_CLOSED = 5` (§3.4). Neither deprecated status slashes a Connector.
- State proven between ledgers (for example the Hiero `ClprChannel` leaf) keeps its current numbering, including
  deprecated fields.

## 4. Why This Is The Right Solution

The main-branch specification asks every implementation to complete four structural migrations at once. This ADR keeps
only the changes that are implemented or deliverable by the cut-off, and it removes two sources of cross-ledger
incompatibility: the mismatch between specification and implementations, and the divergence between the
implementations themselves.

Requiring every Data Message to be answered before `DRAINED`, and the peer's whole proven queue to be received before
a bundle moves the Channel to `CLOSED`, closes the gap that bounded bundles open: the receiver decides from its own
outbound queue and the peer's proven queue, not from the peer's status, that nothing it is owed is still in flight.

Returning the bundle's last message ID and running hash beside the sender's proven Channel state keeps what
`2026-07-17` was trying to achieve, bounded bundles that can always make progress on any backlog, while keeping the
data structure the Hiero implementation already proves. The verifier proves the last included message's running-hash entry in
addition to the Channel state.

Dropping mTLS in favour of client-negotiated TLS on one port removes the only in-spec requirement that no pair of
implementations currently meets. Integrity never depended on the transport, so nothing is weakened; confidentiality
against passive observers is retained.

Documenting the implemented wire format, rather than changing it, keeps 0.2 interoperable without a lockstep migration
before the cut-off. The implementations already agree on the field numbering, the endpoint fields and the running hash.
The deprecated fields and values stay accepted, so no implementation rejects another's messages, other than a redacted
payload, which fails the EVM running-hash check (§3.4); redaction SHOULD NOT be used until its removal.

## 5. Testing

1. Hiero → EVM and EVM → Hiero: a backlog larger than `max_messages_per_bundle` drains across multiple bundles, each
   carrying a prefix.
2. A bundle whose first message ID is below `received_message_id + 1` (overlap) is accepted; overlapping messages are
   skipped and not re-dispatched.
3. A bundle whose first message ID is above `received_message_id + 1` (gap) is rejected.
4. A bundle whose `last_message_running_hash` does not match the folded hash is rejected.
5. A bundle with zero messages that advances only acknowledgement, status, trust anchor, or manifest is accepted; one
   that advances none is rejected with `NoProgress`.
6. `m.received_message_id` greater than the local `Channel.next_message_id − 1`, or below the local
   `Channel.acked_message_id`, is rejected.
7. Running hash test vectors agree across Hiero, EVM Solidity, and both endpoint implementations using
   `SHA-256(prev ‖ SHA-256(serialized_payload))`.
8. A Hiero endpoint and an EVM endpoint complete a two-phase `sync` in both initiator roles.
9. A client connects over TLS to a TLS server, and falls back to plaintext against a plaintext-only server, on the
   same advertised port.
10. A server never requests a client certificate; a client presenting none succeeds.
11. `completeChannel` without an endpoint manifest proof starts the Channel at manifest version 0, and the first
    manifest-carrying bundle installs the peer manifest; manifest refresh via `verifyBundle` works on both chains.
12. `ClprLedgerConfiguration` and `ClprEndpointManifest` serialized by Hiero are decoded by the EVM verifiers and
    vice versa; a populated `endpoints = 6` and non-empty `tls_certificate` / `account_id` are accepted.
13. A `CLOSING` Channel whose Data Messages are all acknowledged but not all answered stays `CLOSING` until the last
    Response arrives, then reaches `DRAINED` in that same bundle.
14. A `DRAINED` Channel whose peer reports `DRAINED` stays `DRAINED` until it has received every message in the
    peer's proven queue, then reaches `CLOSED`.
15. Admin `closeChannel` on a `DRAINED` Channel with unacknowledged outbound messages is rejected; once
    `acked_message_id ≥ next_message_id − 1` it succeeds. On a `CLOSING` or `CLOSED` Channel it is rejected.
16. A configuration update made while a Channel is `CLOSING` or `DRAINED` enqueues no `ConfigUpdate` on it, and the
    Channel still reaches `CLOSED`.
17. Admin `closeChannel` on an `ACTIVE` Channel with no unanswered Data Message reaches `DRAINED` in the same call.

## Appendix B: Implementation Conformance

### Hiero implementation

- Remove the endpoint-manifest enable flag and the seed-endpoint `verifyConfig(bytes,bytes32)` path.
- Running hash, `ClprLedgerConfiguration` numbering (including `endpoints = 6`), `ClprEndpoint` fields, redaction and
  `CHANNEL_CLOSED`, and proven state numbering (e.g. the `ClprChannel` leaf): no change (§3.4, §3.6). Redaction
  SHOULD NOT be used.
- `ClprEndpointService` definition: expose the two-phase stream as `sync`; remove the unary `sync` and
  `streamingSync`. The endpoint synchronizer must initiate the two-phase stream.
- Transport: remove mTLS (the dedicated mTLS port, required client authentication on the gRPC server, and the
  CA certificate manager); serve `ClprEndpointService` on the one advertised port with server-auth TLS; client
  TLS-first with plaintext fallback.
- `ClprQueueMetadata`: bundle verification and bundle submission carry the sender's
  Channel state (§3.3.1); consume `last_message_id` and `last_message_running_hash` per §3.3.5, which are `0` and
  empty for a bundle with no messages.

### clpr-smart-contracts

Implemented:

- Prefix bundles per §3.3: `verifyBundle` returns `last_message_id` / `last_message_running_hash`, and
  `DRAINED → CLOSED` waits for the peer's whole proven queue.
- A populated `ClprLedgerConfiguration.endpoints = 6` is skipped rather than rejected.
- `HieroVerifier` rejects a Merkle path that carries more than one content arm, so a leaf's hash is computed from its
  own bytes, and binds the proven `ClprChannel` leaf to `ctx.channel_id`.
  Earlier message leaves are secured by the running-hash chain.
- Step 5c config propagation runs only on a Channel that was `ACTIVE` or `PAUSED` when the bundle arrived (§3.3.5).
- `CLOSING → DRAINED` once every Data Message is answered, `closeChannel` reaching `DRAINED` in the same call, and
  the admin `DRAINED → CLOSED` path only once every outbound message is acknowledged (§3.3.6).

Retained and documented, no change for 0.2:

- Running hash `SHA-256(prev ‖ SHA-256(serialized_payload))`; the receiver hashes the payload bytes it receives (§3.4).
- `ClprLedgerConfiguration` trust-anchor fields at 7 and 8 (§3.6).
- `ClprEndpoint.tls_certificate` and `account_id`, with the structural DER X.509 / RSA-modulus check on a non-empty
  certificate (§3.1.3).
- `redactMessage`, payload variant 4, `REDACTED` and `CHANNEL_CLOSED` (deprecated). The Solidity-only
  `ReplyStatus.NOT_HANDLED = 6` is never produced, but a received reply status of 6 is accepted without a slash.
- `completeChannel` without a manifest proof starts the Channel at manifest version 0 (§3.5).
- A bundle whose `received_message_id` is below the Channel's `acked_message_id` is rejected.
