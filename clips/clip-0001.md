# CLIP-0001: CLPR Specification Governance and Organization

## 1. Introduction

The CLPR Specification defines how independent implementations of CLPR, on many ledgers, interoperate. Implementations are built by different teams and organizations in separate repositories. To stay compatible they need one shared definition of the specification, clear versions of it, and a predictable way for it to change.

This document defines:

1. **The foundation:** the license, roles, and decision-making the specification is governed under (Section 2).
2. **The specification:** what it contains and how the repository is organized (Section 3).
3. **Versions:** what a version is, and how branches and tags represent versions (Section 4).
4. **Making changes:** the everyday contribution workflow, and which changes need what approval (Section 5).
5. **CLIPs:** CLPR Improvement Proposals, the vehicle for changes to the protocol (Section 6).
6. **Integration and release:** how accepted CLIPs become specification text and then a released version (Section 7).

CLIP-0001 is the single source of truth for this process. When adopted, its status is **Living**: it is amended in place rather than replaced (Section 8). Section 9 gives examples of the process in use. Section 10 is a glossary of the terms introduced along the way.

Requirement keywords **MUST**, **SHOULD**, and **MAY** follow RFC 2119.

## 2. Foundation: The Community Specification

### 2.1 License and scope

The CLPR Specification is developed under the **Community Specification License 1.0 (CSL)** and the Community Specification framework of the Linux Foundation, as required for specifications in LF Decentralized Trust (LFDT).

- Contributions are made under CSL terms, including its patent commitments and its process for patent exclusion notices.
- `SCOPE.md` defines what the specification covers: everything described in Section 3 of this document. All of it is under the same license and patent terms.

### 2.2 Roles

The specification uses the CSL roles.

| Role | Responsibilities |
|---|---|
| **Participant** | Anyone contributing under CSL terms. Any Participant may open issues, submit pull requests, and author CLIPs. |
| **Editor** | Keeps the specification text accurate, consistent, and in line with decisions. Checks CLIPs for completeness and format, and assigns CLIP numbers. Writes or reviews integration pull requests. Gives final approval before changes are merged. |
| **Maintainer** | Determines consensus. Decides the progress of CLIPs and which CLIPs go into each version. Manages releases. Maintains the specification on behalf of the LFDT project, independently of any one vendor. |

A Maintainer's authority may be **scoped** to part of the repository, such as one ledger's specifications. Scopes are recorded in `MAINTAINERS.md` and enforced with `CODEOWNERS`. The project aims for Maintainers from multiple organizations.

### 2.3 Decisions

Decisions follow CSL governance. Maintainers determine consensus in good faith from the discussion. Unanimity is preferred but not required. Disagreements may be appealed as described in `GOVERNANCE.md`.

### 2.4 Governance files

| File | Contents |
|---|---|
| `LICENSE.md` | The CSL 1.0 license |
| `SCOPE.md` | What the specification covers |
| `NOTICES.md` | Notices, including patent exclusion notices |
| `GOVERNANCE.md` | CSL governance: roles, consensus, appeals |
| `CONTRIBUTING.md` | CSL contribution policy; refers to this document for CLIPs and repository organization |
| `MAINTAINERS.md` | Current Maintainers, Editors, and Maintainer scopes |
| `CODE_OF_CONDUCT.md` | Code of conduct |

The CSL files define *who* decides and *how decisions are made*. This document defines *what* the specification is and *how it changes*. The two do not repeat each other.

## 3. The Specification

### 3.1 Overview and categories

`clpr-overview.md` is the entry point to the specification. It is non-normative. It describes the major parts of CLPR and how they fit together, and defines CLPR's vocabulary (ledger, CLPR Endpoint, connector, channel, message, bundle, verifier contract, CLPR Service).

The normative content is divided into three **categories**. They differ in who must agree on the content, and in what breaks if they do not.

| Category | Level | Applies to | If implementations disagree |
|---|---|---|---|
| **Protocol** | MUST | Every implementation on every ledger | Interoperability between ledgers breaks |
| **Ledger Specifications** | MUST | Anyone interoperating with that ledger | Interoperability with that ledger breaks |
| **Blueprint** | SHOULD | Individual CLPR deployments | Nothing; deployments may differ freely |

### 3.2 Protocol

The **Protocol** defines interoperability across all ledgers. Changes to it define the versions of the specification (Section 4).

It is divided into **modules**, each covering one topic, such as channel setup, connector setup, messaging, CLPR Endpoint sync, and channel state transitions. One module may change in a version while the others do not.

The Protocol is written in terms of **abstract data structures**: structures defined by their fields and meaning, not by any encoding. How each ledger represents them is defined in its Ledger Specifications. The exception is **CLPR Endpoint sync**, the protocol CLPR Endpoints on different ledgers use to communicate directly. It is the one concrete wire protocol that all CLPR Endpoints implement, so its module includes machine-readable wire definitions.

Two Protocol modules are central to the Ledger Specifications:

- **Bundle:** the abstract content a bundle conveys from one ledger to another.
- **Verifier interface:** the abstract interface of a verifier contract. Verifier contracts are stateless. A verifier takes a bundle and a **trust anchor** as input, and returns the verified bundle content and, when the trust anchor changes (for example after a roster change), a new trust anchor. Trust anchors are stored with the channel, not in the verifier contract.

### 3.3 Ledger Specifications

**Ledger Specifications** continue the specification at the level of detail of one ledger. They describe how bundle content is gathered from a ledger, how it is proven and laid out on the wire, how it is verified on another ledger, and how verified content is handed to the CLPR Service.

The path of a bundle, and where each step is specified:

```
 Source ledger: CLPR Endpoint
   chain state
     │  bundle aggregation ............ ledgers/<source>/bundle-aggregation.md
     ▼
   abstract bundle content ............ protocol/bundle.md
     │  proof material + encoding ..... ledgers/<source>/proof-schemes/<scheme>.md
     ▼
   bundle (wire layout)
     │  endpoint sync ................. protocol/endpoint-sync/
     ▼
 Destination ledger: CLPR Service and verifier contract
   bundle + trust anchor stored with the channel
     │  decode and verify ............. ledgers/<source>/proof-schemes/<scheme>.md
     │  called through ................ ledgers/<destination>/verifier-api.md
     ▼
   abstract bundle content + new trust anchor (if changed)
     │  channel state transitions ..... protocol/channel-state-transitions.md
     ▼
   updated channel state
```

Each ledger's specifications contain three kinds of document:

- **Verifier API** (`verifier-api.md`): the concrete API that every verifier contract deployed on this ledger implements, and that this ledger's CLPR Service calls. It is this ledger's binding of the Protocol's verifier interface, written in the idioms of the ledger's contract language (for example, optional types in one language, sentinel values in another). Each ledger has exactly one verifier API.
- **Bundle aggregation** (`bundle-aggregation.md`): the algorithm a CLPR Endpoint on this ledger follows to gather the abstract bundle content from chain state.
- **Proof schemes** (`proof-schemes/<scheme>.md`): a ledger may have several. A **proof scheme** defines what is proven about the bundle content, how, and how a remote verifier checks it. Different finality rules, consensus configurations, attester sets, or zero-knowledge proofs are different proof schemes.

A proof scheme specification contains:

1. **Trust model:** what is proven, with what finality, and what an attacker would have to compromise.
2. **Proof material:** what the CLPR Endpoint collects in addition to the abstract bundle content.
3. **Wire layout:** the concrete layout of data and proof in the bundle. Each scheme defines its own layout, so data and proof can be arranged to suit its verification algorithm.
4. **Encoding algorithm:** how the CLPR Endpoint builds the bundle.
5. **Decode-and-verify algorithm:** how a verifier contract decodes the bundle, verifies the proof, and produces the abstract bundle content and any new trust anchor. Written in pseudocode, because it is implemented in each destination ledger's contract language.
6. **Trust anchor changes:** when and how the trust anchor changes, if it does.
7. **Rejection conditions:** every condition under which verification fails.

Pseudocode follows the notation in `protocol/conventions.md`.

A **verifier contract** always combines two Ledger Specifications: a proof scheme of the source ledger (what it decodes and verifies) and the verifier API of the destination ledger (what it implements).

Two arrangements avoid duplication:

- **Families.** Ledgers that share an execution environment share one verifier API, kept in a family directory such as `ledgers/evm/`. Each ledger's `README.md` states which verifier API applies to it.
- **Generic proof schemes.** Schemes that do not depend on a ledger's consensus, such as M-of-N attesters, are kept in `ledgers/generic/` and combined with any ledger's bundle aggregation.

### 3.4 Blueprint

The **Blueprint** describes how a working CLPR deployment is recommended to be built and to behave. Examples include the design of the CLPR Service and its internal state (expressed as abstract data structures), stakes and bonds, channel economics, and ledger-locked data structures.

Blueprint content is SHOULD. Deployments may depart from it without affecting interoperability. It is kept in the specification repository because it is the reference for what a complete, working CLPR deployment looks like.

## 4. Versions and Branches

### 4.1 Specification versions

A **specification version** is a released, unchanging definition of the Protocol, identified by a version number. Before the first major version, versions are numbered v0.1, v0.2, v0.3, and so on. From v1 onward they are whole numbers: v1, v2, v3. Versions are ordered, and each one is incompatible with the others, including pre-1.0 versions: implementations interoperate only when they implement the same version.

A version is prepared on the `main` branch. When the Maintainers decide what it will contain, they declare a **scope freeze**. A **release candidate** is then tested by implementers, and finally the Maintainers declare the version **final**. Section 7 describes these steps in detail.

Each Protocol module records, in its header, the version in which it last changed (for example, "Last changed: v2"). This shows implementers which modules a new version affects without a separate numbering scheme for each module. Each module ends with a history section listing the CLIPs that changed it, by version.

### 4.2 Branches and tags

- `main` always holds the next version under development.
- When a version becomes final, a branch `release/vN` is created from `main`. It holds that version from then on.

| Tag | Marks |
|---|---|
| `vN-rc.K` | Release candidate K of version N, on `main` |
| `vN` | The final release of version N, at the start of `release/vN` |
| `vN-rK` | Revision K of version N, on `release/vN` |

### 4.3 What changes on a version branch

The Protocol text on a version branch does not change, except for:

- **errata:** corrections that do not change the behavior the text was intended to specify, and
- **security fixes** (Section 7.3).

Ledger Specifications and the Blueprint continue to change on version branches. New ledgers, new proof schemes, and changes forced by a ledger's own upgrades are added to every version branch they apply to, and to `main`. Ledger Specifications map a version's abstract data structures to concrete formats, so the same change may be written differently on different branches.

Every Ledger Specification document carries a **revision number** in its header, counted separately on each branch. The number increases whenever the document changes in a way implementations must act on. A Ledger Specification is identified by version, path, and revision, for example: *v2, `ledgers/ethereum/proof-schemes/finalized.md`, revision 3*.

Maintainers tag a new revision of the branch (`vN-rK`) when they publish changes, so implementations can refer to a fixed state of the branch.

### 4.4 Implementations

Each implementation repository declares what it implements in a **conformance manifest**.

A CLPR Service and CLPR Endpoint:

```yaml
# CLPR-CONFORMANCE.yaml
implementation: hiero-clpr
spec: v2-r3                      # specification version and branch revision
ledger: hiero
verifier-api: ledgers/hiero/verifier-api.md @ revision 1
proof-schemes:                   # outgoing schemes this endpoint produces
  - ledgers/hiero/proof-schemes/hints-wraps.md @ revision 2
blueprint-deviations: []         # departures from the Blueprint, if any
```

A verifier contract:

```yaml
verifier: ethereum-finalized-on-hiero
spec: v2-r3
consumes: ledgers/ethereum/proof-schemes/finalized.md @ revision 3
implements: ledgers/hiero/verifier-api.md @ revision 1
```

An implementation that supports more than one specification version keeps a maintenance branch for each older version (for example `clpr-v2`), where bug fixes and new verifier contracts continue to land.

## 5. Making Changes

### 5.1 The CSL workflow

All changes start in the CSL contribution workflow of issues and pull requests.

CSL defines three kinds of issue: **Discussion** (questions and ideas), **Proposal** (a proposed change, before it is written up), and **Spec Change** (a specific change to the text). The repository uses labels to track them:

| Label | Meaning |
|---|---|
| `discussion`, `proposal`, `spec-change` | The CSL issue type |
| `editorial`, `errata` | Wording or correction that does not change behavior |
| `protocol`, `blueprint`, `ledger:<name>`, `process` | The area affected |
| `clip` | Tracks a CLIP |
| `applies-to:vN` | Must also be applied to `release/vN` |
| `needs-maintainer-approval` | Requires approval beyond the Editor (Section 5.2) |
| `notice` | Advance notice of a change that affects other implementers |

Each version under preparation has a **milestone**. Pull requests that integrate CLIPs into that version are assigned to it.

### 5.2 What each change needs

| Change | Vehicle | Approval | Lands on |
|---|---|---|---|
| Protocol behavior | CLIP, then an integration pull request | Maintainers, through the CLIP lifecycle | `main` |
| Protocol errata | Pull request | Editor | Affected `release/vN` branches and `main` |
| Protocol security fix | Private fix, then a CLIP | Maintainers (Section 7.3) | Affected `release/vN` branches and `main` |
| New ledger, new proof scheme, or other additive Ledger Specification change | Pull request | The ledger's scoped Maintainers and an Editor | Every branch it applies to, and `main` |
| Verifier API change, or a proof scheme change that existing verifiers cannot accept | Pull request with a `notice` issue | The ledger's scoped Maintainers and a Protocol Maintainer | Every branch it applies to, and `main` |
| Blueprint | Pull request | Editor | Any branch it applies to |
| Editorial change anywhere | Pull request | Editor | Any branch |
| Process | Pull request amending CLIP-0001 | Maintainers, after Last Call (Section 8) | `main` |

Only Protocol behavior changes need a CLIP, because only they define versions. A change to a verifier API or an incompatible change to a proof scheme does not need a CLIP, but it needs a Protocol Maintainer's approval and advance notice, because verifier contracts maintained by others depend on it.

## 6. CLIPs

### 6.1 What a CLIP is

A **CLIP** (CLPR Improvement Proposal) is a document proposing a change to the Protocol, together with its reasoning and the record of its decision. CLIPs are stored permanently in `clips/`, including those that are rejected or withdrawn, so the history and reasoning behind the specification stay available after the issues and pull requests that discussed them are closed.

A CLIP may change several modules at once. Its front matter lists every module it changes, so its scope is visible. A CLIP is scheduled into a version, integrated, and released as a whole: a version never contains part of a CLIP.

A CLIP is not normative. Once integrated, the specification text is the definition; the CLIP remains as the explanation of how and why it changed.

### 6.2 Structure

A CLIP tells the story of a change in order: the problem, the options considered, the solution, and what it changes.

1. **Abstract.** A short summary of the problem and the proposed change.
2. **Problem.** What is wrong, missing, or limiting in the current specification.
3. **Approaches considered.** The range of possible approaches, briefly, and the drawbacks of each one not chosen. Ends with the **requirements** an adequate solution must meet.
4. **Proposed solution.** The solution in full, showing how it meets the requirements.
5. **Specification changes.** The changes to the specification text, organized by module. This is what integration will do.
6. **Compatibility and migration.** The effect on implementations, on Ledger Specifications, and on existing channels, and how to move from the base version to the new one.
7. **Security considerations.**
8. **Implementation advice.** *Optional.* Suggested schedule, reference implementations, or practical notes.
9. **Open issues.** Unresolved questions. *Required while in Draft, and resolved before Last Call.*
10. **References.** *Optional.*

`clips/clip-template.md` lays out these sections with guidance for each.

### 6.3 Front matter

```yaml
clip: 42
title: <short title>
authors: <names>
status: Draft
discussion: <issue URL>
base-release: v2                  # the version this CLIP was written against
target-release: unscheduled       # or v3, once Scheduled
modules:                          # every Protocol module this CLIP changes
  - protocol/messaging.md
  - protocol/endpoint-sync
ledger-impact:                    # Ledger Specifications that must change with it
  - ledgers/hiero/bundle-aggregation.md
requires: []                      # other CLIPs this one depends on
supersedes: []
superseded-by:
created: YYYY-MM-DD
```

### 6.4 Lifecycle

```
                                      ┌─────── unschedule ────────┐
                                      ▼                           │
Draft ──► Review ──► Last Call ──► Accepted ──► Scheduled ──► Integrated ──► Final ──► Superseded
```

In addition, a CLIP may become **Withdrawn**, **Rejected**, or **Deferred** from any state before Final. A Deferred CLIP may return to Draft.

A CLIP is merged into `clips/` as a Draft as soon as it is complete enough to discuss, so it is part of the repository from the start. Each later change of status is a pull request that updates its front matter.

| Transition | Decided by | Requirements |
|---|---|---|
| New → Draft | Editor | All required sections present, even if incomplete. Editor assigns the number. |
| Draft → Review | Author | Solution, specification changes, and compatibility sections complete |
| Review → Last Call | Maintainers | Discussion has settled; open issues resolved |
| Last Call → Accepted | Maintainers | Last Call period (default 14 days) has ended; Maintainers determine consensus. Accepted means the design is approved, not that it is in a version. |
| Accepted → Scheduled | Maintainers | Assigned to a version that has not reached scope freeze |
| Scheduled → Integrated | Editor | Integration pull request merged (Section 7.1) |
| Integrated → Final | Maintainers | The version is declared final |
| Scheduled or Integrated → Accepted | Maintainers | Removed from the version; any integrated text is reverted |
| → Withdrawn | Author | Author abandons the CLIP |
| → Rejected | Maintainers | Consensus is against the CLIP |
| → Deferred | Maintainers | No one is actively pursuing it, or the timing is wrong |
| Deferred → Draft | Any Participant | Someone takes it up again |
| Final → Superseded | Maintainers | A later Final CLIP replaces it |

### 6.5 Rules

| # | Rule | Reason |
|---|---|---|
| 1 | **Implement released versions, not `main`.** Implementations target final versions or release candidates. | Interoperability needs a fixed target that everyone shares. |
| 2 | **Accepted is not Scheduled.** Approving a design and putting it into a version are separate decisions. | They need different information: whether a design is right, and whether a version can absorb it now. |
| 3 | **No scheduling after scope freeze.** | Implementers need a stable target in time to build and test it. |
| 4 | **A CLIP declares its base release.** If that version is superseded before the CLIP is scheduled, the CLIP is updated to the current text. | The text a CLIP changes is unambiguous. |
| 5 | **A CLIP is scheduled, integrated, and released as a whole.** | A version means the same thing to every implementation. |
| 6 | **Scheduling can be reversed until the version is final.** | A problem found during testing is cheaper to defer than to ship. |
| 7 | **Integration is part of done.** A CLIP is not Final until the specification text is updated. | Readers read one specification, never a base text plus a series of changes. |
| 8 | **The specification is authoritative.** When an implementation and the specification disagree, the implementation changes or a CLIP changes the specification. | All implementations converge on one definition. |
| 9 | **Unreleased work uses experimental identifiers.** Wire identifiers, message types, and contract selectors become stable only in a final version. | Prototypes cannot be mistaken for released behavior or interoperate with it by accident. |

## 7. Integration and Release

### 7.1 Integration

**Integration** is the step where a CLIP's specification changes become specification text. It is done in a single pull request, written or reviewed by an Editor, which:

- edits every module listed in the CLIP's front matter,
- updates the "Last changed" header and history section of each changed module,
- makes any Ledger Specification changes on `main` listed under `ledger-impact`, reviewed by the scoped Maintainers of those ledgers, and
- changes the CLIP's status to Integrated.

### 7.2 Releasing a version

A version moves through these states on `main`:

| State | What happens | Ends when |
|---|---|---|
| **Open** | CLIPs are Scheduled into the version and integrated. | Maintainers declare scope freeze. |
| **Scope Frozen** | No further CLIPs can be Scheduled. Remaining Scheduled CLIPs are integrated or unscheduled. | All Scheduled CLIPs are integrated, and Maintainers tag the first release candidate. |
| **Release Candidate** | The text is frozen and tagged `vN-rc.K`. Implementers build and test against it. Only fixes are made; a CLIP that proves unworkable is unscheduled, and a new release candidate is tagged. | Maintainers declare the version final. |
| **Final** | Tagged `vN`. Branch `release/vN` is created. Its CLIPs become Final. Release notes are published in `releases/vN.md`. `main` becomes Open for version N+1. | Maintainers deprecate it after a later version is final. |
| **Deprecated** | `release/vN` still receives errata, security fixes, and Ledger Specification changes. Implementers are encouraged to move to a later version. | Maintainers retire it. |
| **Retired** | No further changes. | — |

While a version is a release candidate, CLIPs may be Scheduled for the next version, but are not integrated until the current version is final.

How CLIP statuses relate to the state of the version they are scheduled into:

| Version state | CLIP statuses in that version |
|---|---|
| Open | Scheduled, Integrated |
| Scope Frozen | Scheduled (being integrated), Integrated |
| Release Candidate | Integrated |
| Final | Final |

In CSL terms, a version in Release Candidate is a Draft Specification, and a Final version is an Approved Specification.

### 7.3 Security fixes

A vulnerability in a released version may be fixed privately, without public discussion or Last Call. Maintainers apply the fix to each affected `release/vN` branch and to `main`, tag new revisions, and publish the CLIP describing the fix at the same time. This is the only case in which a version's Protocol behavior may change after it is final; every implementation of that version is expected to adopt the fix.

## 8. Amending CLIP-0001

CLIP-0001 is a bootstrap document. It describes the process instead of changing the Protocol, so it does not follow the CLIP template, and it does not move through Scheduled or Integrated.

Once adopted, its status is **Living**. Changes to the process are made by amending this document directly, so it always describes the current process in full:

- An amendment is a pull request to `clips/clip-0001.md`, labeled `process`.
- It goes through a Last Call (default 14 days) and is approved by the Maintainers.
- Each amendment is recorded in the change history at the end of this document.

## 9. Examples

**A protocol change, start to finish.**
A Participant opens a Proposal issue about a limitation in the messaging protocol, and then writes CLIP-0042. An Editor checks it, assigns the number, and merges it as Draft. The author completes it and moves it to Review. After discussion, the Maintainers move it to Last Call and then Accepted. They schedule it into v3, which is Open on `main`. An Editor merges the integration pull request: `protocol/messaging.md` is updated, its header now reads "Last changed: v3", and CLIP-0042 is Integrated. The Maintainers declare scope freeze and tag `v3-rc.1`. Implementers build and test against it. The Maintainers declare v3 final: `release/v3` is created, CLIP-0042 becomes Final, and implementations update their conformance manifests to `spec: v3`.

**A large CLIP after scope freeze.**
CLIP-0050 proposes redesigning CLPR Endpoint sync after v3 has reached scope freeze. It continues through Review and Last Call and may be Accepted, but it cannot be Scheduled into v3 (rule 3). Its target release stays `unscheduled`. When v3 is final, its base release (v2) is out of date, so the author updates it to the v3 text (rule 4), and the Maintainers schedule it into v4.
If CLIP-0050 would make CLIPs already scheduled for v3 pointless, the Maintainers choose between shipping v3 as planned or unscheduling the affected CLIPs (rule 6) and re-planning v3. The decision is recorded in the v3 release notes.

**A CLIP removed during the release candidate.**
While testing `v3-rc.1`, implementers find that CLIP-0047 cannot be implemented efficiently on one ledger. The Maintainers move it back to Accepted, an Editor reverts its text, and `v3-rc.2` is tagged without it. CLIP-0047 can be revised and scheduled into a later version.

**Building ahead of a release.**
A team wants to demonstrate CLIP-0050 before it is released. They may build it using experimental identifiers (rule 9). The prototype cannot be declared in a conformance manifest and cannot interoperate with released implementations by accident. If a demonstration needs several components to work together on unreleased changes, the Maintainers tag an early release candidate so every team builds against the same frozen text.

**An Ethereum upgrade changes a proof scheme.**
An Ethereum hard fork changes the structure of the state proofs used by the `finalized` proof scheme. The verifier API and the Protocol do not change.
1. Once the fork's own specification is stable, an Ethereum scoped Maintainer opens a pull request against `ledgers/ethereum/proof-schemes/finalized.md`, with a `notice` issue, because existing verifiers cannot accept the new proofs.
2. The scheme's decode-and-verify algorithm handles both the old and new proof structures, selected by block height, so bundles from either side of the fork can be verified. Its revision increases, for example from 2 to 3.
3. The change is labeled `applies-to:v2` and `applies-to:v3` and is made on `release/v2`, `release/v3`, and `main`. The ledger's scoped Maintainers and a Protocol Maintainer approve it. New branch revisions are tagged.
4. Verifier authors on every destination ledger release verifiers that declare `consumes: ledgers/ethereum/proof-schemes/finalized.md @ revision 3`, and deploy them before the fork activates.

**A new proof scheme for an existing ledger.**
A contributor adds a zero-knowledge proof scheme for Hiero. They open a pull request creating `ledgers/hiero/proof-schemes/<scheme>.md`. Adding a scheme does not affect existing verifiers, so it needs only the Hiero scoped Maintainers and an Editor. It is applied to every version branch it supports.

**Another organization adds a ledger.**
An organization wants CLPR on a new ledger. It opens a pull request creating `ledgers/<ledger>/` with a `README.md`, bundle aggregation, at least one proof scheme, and either its own verifier API or a reference to a family's. Its engineers become scoped Maintainers for that directory. No new specification version is needed. The ledger is added to each version branch it supports.

**A security fix to an older version.**
A vulnerability is found in v2 after v3 is final. The Maintainers fix it privately on `release/v2`, `release/v3`, and `main`, tag `v2-r4` and `v3-r1`, and publish the CLIP describing the fix. Implementations of v2 apply the fix on their `clpr-v2` maintenance branches.

**A deployment departs from the Blueprint.**
A ledger's CLPR deployment uses different channel economics from those in `blueprint/channel-economics.md`. No change to the specification is needed. The implementation lists the departure under `blueprint-deviations` in its conformance manifest, and remains fully interoperable.

## 10. Glossary

| Term | Definition | Section |
|---|---|---|
| Blueprint | SHOULD-level guidance on building a CLPR deployment; departures do not affect interoperability | 3.4 |
| Bundle aggregation | The algorithm a CLPR Endpoint follows to gather abstract bundle content from its ledger's chain state | 3.3 |
| Category | One of Protocol, Ledger Specifications, or Blueprint | 3.1 |
| CLIP | CLPR Improvement Proposal: a permanent document proposing a Protocol change | 6.1 |
| Conformance manifest | A file in an implementation repository declaring what it implements | 4.4 |
| Editor | CSL role responsible for the accuracy of the text and for integration | 2.2 |
| Errata | A correction that does not change intended behavior | 4.3 |
| Family | Ledgers sharing an execution environment, and therefore one verifier API | 3.3 |
| Integration | Turning a CLIP's specification changes into specification text | 7.1 |
| Ledger Specifications | MUST-level specifications for interoperating with one ledger | 3.3 |
| Maintainer | CSL role that determines consensus, decides CLIPs and versions, and manages releases | 2.2 |
| Module | One topic of the Protocol, kept in one document | 3.2 |
| Participant | Anyone contributing under CSL terms | 2.2 |
| Proof scheme | A definition of what is proven about bundle content, its wire layout, and how a remote verifier checks it | 3.3 |
| Protocol | MUST-level specification of interoperability across all ledgers; defines versions | 3.2 |
| Release candidate | A frozen pre-release of a version, tagged `vN-rc.K`, for implementers to test | 4.1, 7.2 |
| Revision | A numbered change to a Ledger Specification document, or a tagged state of a version branch | 4.3 |
| Scope freeze | The point after which no CLIPs can be Scheduled into a version | 4.1, 7.2 |
| Scoped Maintainer | A Maintainer whose authority covers part of the repository | 2.2 |
| Specification version | A released, unchanging definition of the Protocol, numbered v0.N before v1 and by whole numbers from v1 | 4.1 |
| Trust anchor | The state a verifier needs to check proofs, stored with the channel and possibly updated by each verification | 3.2 |
| Verifier API | A ledger's concrete binding of the verifier interface | 3.3 |
| Verifier contract | A stateless contract on a destination ledger that verifies bundles using one proof scheme | 3.3 |
| Verifier interface | The abstract interface of verifier contracts, defined in the Protocol | 3.2 |
